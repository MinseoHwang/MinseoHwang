# Remy 결제 응답 유실 후 거래 조회와 복구

[Remy 개요·기여 범위](README.md) · [환불·재고 사례](refund-inventory.md)

## 문제

PG에서 결제가 승인됐지만 응답을 받지 못하면 서버는 결제 성공 여부를 알 수 없습니다. 이 상태에서 승인을 다시 요청하거나 재고를 바로 풀면 중복 결제나 이미 결제한 티켓의 재판매로 이어질 수 있습니다.

## 프로젝트의 구현과 판단

승인 진입권을 얻는 DB 처리, PG 호출, 결과를 반영하는 DB 처리를 나눴습니다. 외부 요청을 기다리는 동안 DB 트랜잭션을 유지하지 않는 구조입니다. 조건부 상태 변경과 활성 결제의 유일 제약으로 중복 진입을 제어합니다.

```text
READY → APPROVING → 승인 결과 반영
            │
            └─ 응답 불명 → IN_DOUBT → 거래 조회
                                         ├─ 결과 확인 → 상태 반영
                                         └─ 미해결 → 재조회 / 운영 검토
```

복구 작업은 PostgreSQL의 `FOR UPDATE SKIP LOCKED`로 대상을 선점합니다. 선점 유효기간과 복구 토큰을 저장하고, 작업자가 바뀐 뒤에는 이전 토큰으로 승인 복구 상태를 갱신하지 못하도록 조건을 둡니다.

조회 결과가 없다는 이유만으로 실패를 확정하지 않습니다. 조회 간격을 제한하고 미해결이 반복되면 대기 시간을 늘리며, 일정 횟수 이후에는 운영 검토로 전환합니다. 고객 화면도 확인 중 상태를 유지합니다.

## 선택의 의미

재승인은 새로운 결제 시도를 만드는 동작이지만, 조회는 이미 보낸 요청의 결과를 확인하는 동작입니다. 복구의 기준을 조회에 두면 통신 오류와 실제 결제 실패를 분리할 수 있습니다. 대신 장시간 미해결 상태를 확인할 운영 경로가 필요합니다.

## 검증 범위

테스트 소스에는 승인 재호출 없이 조회로 복구하기, 이전 복구 토큰 거절하기, 반복 미해결 후 검토로 전환하기가 포함되어 있습니다. 동시 승인 시나리오는 요청 100건을 최대 32개 실행 스레드로 제출해 모의 PG 승인 호출과 활성 결제가 각각 1건인지 검사합니다.

이 통합 테스트는 2026.11.04 검증에서 Docker 엔진 연결 불가로 재실행하지 못했습니다. 요청 수를 TPS나 운영 처리량으로 해석하지 않습니다. 당시 통과한 15개 모의 HTTP 테스트는 별도의 PG 응답 계약 검증입니다.

## 한계

이 문서는 로컬 구현을 설명한 사례입니다. 실제 PG 장애 상황의 복구 성공률, 여러 worker의 경합 결과, 운영 배포와의 일치는 별도 검증이 필요합니다.
