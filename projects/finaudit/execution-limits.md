# 분석과 보고서의 동시 실행 한도 분리

[FinAudit 개요](README.md) · [원본 변경 PR #95](https://github.com/kt-aivle-big-project-13/ai-repo/pull/95)

## 문제

감사 요청이 겹치면 SHAP·공정성 분석과 보고서 생성이 동시에 실행됩니다. 분석은 CPU·메모리를 사용하고, 보고서는 PDF 렌더링을 위해 Chromium을 실행합니다. 요청을 제한 없이 받아들이면 무거운 작업이 중첩됩니다.

## 선택과 구현

동기 FastAPI 라우터의 실행 환경에 맞춰 스레드 세마포어를 적용하고, 분석과 보고서가 별도의 슬롯을 사용하게 했습니다. 하나의 한도를 공유하면 오래 걸리는 보고서 작업 때문에 분석까지 밀릴 수 있기 때문입니다.

슬롯이 없을 때는 한도 내에서 기다립니다. 대기 한도를 넘으면 `503`을 반환해 입력 오류와 일시적인 처리 용량 부족을 구분했습니다. 작업 본문에서 예외가 발생해도 슬롯을 반환하도록 구성했습니다.

```text
분석 요청  → 분석 슬롯 대기  → 분석 실행  → 슬롯 반환
보고서 요청 → 보고서 슬롯 대기 → PDF 생성 → 슬롯 반환
                  │
                  └─ 대기 한도 초과 → 503
```

PR 당시 기본값은 분석 2건, 보고서 1건, 대기 300초였습니다. XGBoost와 BLAS 계열의 스레드 수도 제한했습니다. 이 값들은 환경 설정이며 부하 시험으로 확정한 최적값은 아닙니다.

## 검증

PR에는 허용치 초과 실행 차단, 대기 한도 초과, 본문 예외 후 슬롯 반환, `503` 매핑을 다룬 테스트가 기록되어 있습니다. 해당 변경은 `MinseoHwang` 작성 PR로 병합됐습니다.

2026.11.04 로컬 코드 확인에서도 분석·보고서 풀 분리와 `threading.BoundedSemaphore` 사용을 확인했습니다. 이 문서를 작성하면서 부하 시험을 새로 실행하지는 않았습니다.

## 한계와 후속 확인

- 한도는 프로세스 내부에서 적용됩니다. 여러 프로세스·인스턴스를 합친 전역 실행 한도가 아닙니다.
- 슬롯을 기다리는 시간도 호출자의 타임아웃에 영향을 줍니다. PR 당시 분석 읽기 타임아웃 120초와 대기 상한 300초의 조정은 후속 과제로 남아 있었습니다.
- 다음 측정에서는 실행 시간뿐 아니라 대기 시간·거절 비율·최대 메모리를 함께 확인해야 합니다. 현재 자료로 메모리 감소율이나 응답속도 개선률을 제시하지 않습니다.
